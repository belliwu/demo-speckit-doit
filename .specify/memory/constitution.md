# Demo-Speckit 專案憲法

## 核心原則

### 一、完整測試覆蓋 (不可妥協)

**必須執行**:

- 所有功能必須有單元測試、整合測試及端對端測試
- 測試先行開發 (TDD): 先寫測試 → 測試失敗 → 實作功能 → 測試通過 → 重構
- 最低測試覆蓋率要求 80%,核心業務邏輯必須達 100%
- 每個 Pull Request 必須包含對應測試,未通過測試不得合併

**理由**: 完整測試確保程式品質、降低維護成本,並在重構時提供安全保障。這是專案長期健康發展的基石,不可妥協。

### 二、清楚代碼與註解

**必須執行**:

- 所有函數、類別、模組必須有清楚的註解說明其用途
- 複雜邏輯必須有行內註解解釋原因
- 使用一致的命名規範: 變數用小駝峰 (camelCase)、元件用大駝峰 (PascalCase)、常數用全大寫 (UPPER_CASE)
- 函數名稱必須清楚表達其行為,避免模糊命名

**理由**: 清楚的程式碼和註解降低團隊溝通成本,讓新成員快速上手,並減少因誤解造成的錯誤。

### 三、簡潔使用者體驗

**必須執行**:

- 介面設計遵循直覺性原則,減少使用者學習成本
- 所有互動必須有即時回饋 (載入狀態、錯誤訊息、成功提示)
- 響應式設計必須支援桌面、平板、手機三種裝置
- 操作流程不超過三個步驟,複雜功能須提供引導

**理由**: 良好的使用者體驗直接影響產品成功,簡潔設計讓使用者專注於核心任務,提升滿意度與留存率。

### 四、響應式設計

**必須執行**:

- 使用 Tailwind CSS 實現行動優先 (Mobile-First) 設計
- 斷點設定: 手機 (< 768px)、平板 (768px - 1024px)、桌面 (> 1024px)
- 所有元件必須在三種裝置上測試並正常運作
- 圖片、字體必須根據裝置大小自動調整

**理由**: 現代使用者透過多種裝置存取應用程式,響應式設計確保一致的使用體驗,擴大使用者基礎。

### 五、最小依賴與耦合

**必須執行**:

- 僅使用必要的第三方套件,每個新增套件必須經過評估
- 模組之間保持低耦合,避免循環依賴
- 優先使用內建功能,避免為簡單功能引入大型函式庫
- 定期審查並移除未使用的依賴

**理由**: 減少依賴降低專案複雜度、減小打包體積、降低安全風險,並提升長期維護性。

### 六、模組化架構與單一責任原則

**必須執行**:

- 每個模組只負責一個明確的功能領域
- 每個模組的程式碼行數不超過 500 行,超過須拆分
- 類別與函數遵循單一責任原則 (SRP): 一個類別/函數只做一件事
- 模組之間的互動遵循 GOF 設計模式 (如工廠、策略、觀察者等)
- 資料夾結構反映功能模組,例如: `services/auth/`、`services/dashboard/`
- 依需求複雜度分層架構,包含但不限於:
  - **UI 層 (Presentation Layer)**: 元件、頁面、視覺呈現
  - **控制層 (Controller/API Layer)**: 路由處理、請求驗證、回應格式化
  - **服務層 (Service Layer)**: 業務邏輯、流程編排、跨模組協調
  - **資料存取層 (Data Access Layer)**: ORM 模型、資料庫查詢、快取策略
  - **工具層 (Utility Layer)**: 共用函式、常數定義、型別定義

**理由**: 模組化與 SRP 提升程式碼可讀性、可測試性與可維護性。小型模組易於理解、修改與重用,降低系統複雜度。分層架構確保關注點分離 (Separation of Concerns),使每一層專注於特定職責,便於測試、替換與擴展。

### 七、技術棧一致性

**必須執行**:

- 前端框架: Next.js (App Router)
- UI 函式庫: React 19+
- 樣式方案: Tailwind CSS
- UI 元件: shadcn/ui
- 語言: TypeScript (嚴格模式)
- 所有新功能必須使用上述技術棧,不得引入替代方案

**理由**: 統一技術棧降低學習曲線、簡化開發流程、確保團隊協作效率,並減少整合問題。

## 技術規範

### 強制要求

- **TypeScript 嚴格模式**: 必須啟用 `strict: true`,避免 `any` 型別
- **ESLint 規則**: 使用 Next.js 推薦配置,所有警告必須解決
- **檔案大小**: 單一元件檔案不超過 300 行,單一模組不超過 500 行
- **命名規範**: 元件檔案使用 PascalCase (如 `UserProfile.tsx`),工具函數使用 camelCase (如 `formatDate.ts`)
- **樣式管理**: 只使用 Tailwind 類別,禁止內嵌 CSS-in-JS 或全域樣式 (除 `globals.css`)
- **效能要求**: 首次內容繪製 (FCP) < 1.5 秒,最大內容繪製 (LCP) < 2.5 秒

### 推薦做法

- 使用 Next.js Server Components 作為預設,僅在需要互動時使用 Client Components
- 圖片使用 Next.js `Image` 元件進行最佳化
- 資料請求優先使用 Server Actions,減少客戶端 API 呼叫
- 使用 `loading.tsx` 和 `error.tsx` 處理非同步狀態

## 開發流程

### 功能開發

1. **規格定義**: 使用 `/speckit.spec` 建立功能規格,定義使用者場景與驗收標準
2. **計畫制定**: 使用 `/speckit.plan` 產生實作計畫,檢查是否符合憲法
3. **任務拆分**: 使用 `/speckit.tasks` 將計畫拆分為可獨立測試的任務
4. **測試先行**: 先撰寫失敗測試,確保需求被正確理解
5. **實作功能**: 撰寫最小可行代碼讓測試通過
6. **程式碼審查**: 所有更改必須經過至少一位成員審查
7. **重構優化**: 測試通過後重構代碼,保持簡潔與可讀性

### 品質門檻

每個 Pull Request 合併前必須滿足:

- ✅ 所有測試通過 (單元、整合、E2E)
- ✅ 測試覆蓋率不低於 80%
- ✅ ESLint 無錯誤或警告
- ✅ TypeScript 編譯無錯誤
- ✅ 通過代碼審查
- ✅ 符合憲法原則檢查
- ✅ 效能指標符合要求

## 治理規則

### 憲法優先級

本憲法優先於所有其他開發慣例與文件。若其他文件與憲法衝突,以憲法為準。

### 修訂程序

1. 提出修訂提案,說明理由與影響範圍
2. 團隊討論並投票 (需 2/3 多數同意)
3. 更新憲法版本號 (遵循語義化版本)
4. 同步更新所有相關模板與文件
5. 通知所有團隊成員

### 版本控制規則

- **主要版本 (MAJOR)**: 移除或重新定義核心原則,造成向後不相容
- **次要版本 (MINOR)**: 新增原則、擴充指導方針
- **修訂版本 (PATCH)**: 文字修正、釐清說明,無實質變更

### 合規性檢查

- 所有 Pull Request 必須驗證是否符合憲法原則
- 使用 `.specify/templates/plan-template.md` 的 Constitution Check 段落進行檢查
- 若違反原則必須提供充分理由並記錄於 Complexity Tracking 段落
- 定期審查專案是否持續符合憲法要求 (建議每季一次)
